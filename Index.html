Perfect Fingers

Booking app for a braiding studio

Client project 2026

What it does
Clients choose a service, a date and a time. The studio confirms, completes or cancels each booking and blocks days off from an admin dashboard that shows seven days of revenue. It was built as a custom alternative to a paid scheduling service.
Built with
React 19, Vite, Tailwind CSS, React Router, TanStack Query, Supabase (sign-in, Postgres and row-level security), Recharts and date-fns.
Data and access
Four tables, each with row-level security: profiles, services, blocked dates and appointments. Eleven policies decide who can read or change each row, and the database itself checks roles and booking statuses.
Result
More than 100 real bookings so far.
Next change
Enforce one booking per time slot in the database. Today a taken slot is hidden in the interface, which does not stop two people booking at the same moment.

Ghonsi Proof, a case study

How a Solana product makes work history checkable, and the parts of it I built.

The problem

A line on a CV is easy to write and hard to check. In Web3 much of the work happens in public chats, pseudonymous accounts and short bounties, so a recruiter has little to check a claim against.

Ghonsi Proof lets a professional keep a record of their work that someone else can verify. It was entered in Convergence, a Chainlink hackathon, in the CRE and AI track. The entry lists four builders, and I am one of them.

How a proof travels

  1. Upload

    A professional uploads proof of a piece of work.

  2. Store

    The file goes to decentralised storage.

  3. Anchor

    A cryptographic hash of the file is written to Solana with a timestamp.

  4. Share

    One portfolio link carries the whole record.

  5. Check

    A recruiter reviews the timestamps and the ownership data.

This flow follows the project description on the hackathon page.

My part

I work across the frontend, the Supabase data layer and the payment flows, with three teammates. The parts I can point to:

  • Moving the beta to Next.js. I took the early React and Vite version to Next.js and fixed what broke on the way: environment variable mismatches, hydration errors, and sign-in conflicts between wallet users and email users.
  • Securing the data layer. I worked on the Supabase schemas and row-level security policies, and audited all 49 public tables.
  • Payments that are counted once. Credits are bought with USDT on Solana. I worked on the transfer handling and the backend check, which records each transaction signature so a payment is not credited twice. I also fixed a database function that ignored purchased credits.
  • Wallets for everyone. Wallet users follow Phantom's recommended transaction flow. People who are new to Web3 get a custodial wallet instead.
  • An invite flow for hirers. A hirer can be invited and claim the invite before they have an account, with the claim done in a single atomic database call.
  • The AI chat page. I redesigned it with instant feedback on send, a collapsible sidebar, a slide-in canvas for document generation and a payment modal.

Two decisions

Two kinds of account, one record

Some people arrive with a Phantom wallet and some have never used one. Supporting both meant two sign-in paths that had to end in the same account, and one of the harder problems sat where the two met. The custodial wallet lowers the barrier to entry, and it trades away some self-custody to do it.

Payments need a memory

A transfer on Solana is public, so anyone can copy a signature and present it again. The backend has to remember which signatures it has already counted, and it has to do that before it adds any credit.

How I build

Four habits, each tied to something you can open and read.

Let the database enforce the rules

In Perfect Fingers, row-level security decides who can read or change each row, and the database checks roles and booking statuses. The interface helps people, but it is not the lock.

Check on the server, not in the browser

In Speaking Virtue the backend confirms every payment with the provider and checks webhook signatures. My AuthGuard demo is the counter-example: it makes its one-time code in the browser, which is fine for a demo and wrong for a product.

Design the empty and failed states

In Perfect Fingers a fully booked day says so, and a taken slot disappears instead of failing later. The contact form on this page says a message was sent only when the server confirms it.

Write down what a project does not do

Every project above ends with the change I would make next. A list of limits tells a team what to test first and shows how I think about risk.
